# Integrated 2026.09 RC3 validation

Date: 2026-09-14. Status: **candidate, not promoted to production**. Supersedes RC2 after the [release review](../docs/production-readiness.md) reproduced two revocation retry failures. `versions.lock.yaml` keeps `status: candidate` and `compatibility_verified: false`; the remaining gates are unchanged from RC2 (tenant scopes, public DNS/TLS and OIDC, two-device pilot with a live node expiry).

## Changes since RC2

Only the worker (`sync/worker.py`, `sync/tailnet.py`), its tests and documentation changed. Headscale, Headplane and Casdoor sources and images are identical to RC2 (image IDs `sha256:914ea7582254`, `sha256:1a92413e1ff0`, `sha256:21c82741d585`); their RC3 tags are retags.

| Blocker (RC2 review) | Fix in integration `cf8bf70` |
| --- | --- |
| A partial applied run lost the revocation of a user whose Casdoor block had already been applied; the next plan never re-emitted the block. | Each subject is written to the journal `<state_file>.revocations.json` before its blocking `isForbidden` update is sent. Every applied run, full or staged, revokes journaled subjects plus any linked user forbidden with the worker block or hold marker and without `properties.feishu_sync_revoked`; the marker is written only after Headscale confirmed, so state restored from backup, lost write responses and crashes between block and revocation are recovered. |
| `--offboard --apply` recorded nothing when Headscale failed and did not serialize with the worker. | `--offboard --apply` takes the state lock (bounded by `lock_wait_seconds`), journals the subject with `source: offboard` before blocking, revokes, marks and only then removes the entry; on failure the entry stays and the scheduled worker retries. `--watch` now holds the state lock only while an interval runs (a separate `.watch.lock` still refuses a second continuous worker). |

Related hardening from the adversarial review: a new block by the worker or `--offboard` clears a stale revoked marker (manual re-enable followed by a later block is found even after a journal restore), journal I/O failures in `--offboard` are reported as JSON errors, a `--watch` worker started while offboarding holds the lock retries on its next interval instead of exiting, a journal entry whose block never applied is dropped without touching Headscale, and administrator blocks without markers are never revoked automatically. rc.2 `pending_revocations` state is migrated into the journal once.

## Evidence

- Red/green/review workflow with three independent agents: 21 durability reproductions were written against the interface contract and all failed on RC2 (the two reported sequences failed with alice's nodes 11 and 12 still active after the next successful run and after the failed offboarding); the implementation made them pass; the review added 12 adversarial tests and three minimal fixes. The implementation added 12 tests of its own.
- Integration suite: 180 tests pass (`bash scripts/test.sh`): 132 worker tests (87 from RC2, 45 new), 12 release/restore-safety, 14 bundle, 8 build, 9 proxy, 5 runtime-rendering. Shell syntax and whitespace checks pass.
- Live sandbox (Fysics tenant, staged mode): dry run of the fixed worker reports `revocation: {targets: 0, pending: 0}` with 207/207 users matched and no journal written; `--offboard` dry run on a real account plans the block and one revocation target without writing. The scheduled container was rebuilt from the release commit (see the private inventory for the report).
- RC2 evidence that still applies unchanged: Casdoor authorization probe (bypass on v4.3.0, 8/8 pass on `fde2cf8f`), live staged population (207/207), Headscale API revocation path (provider-identifier match, preauth-key expiry), isolated backup/restore rehearsal (6.6 s / 13.1 s, data identical), Compose rendering; see `2026.09-rc.2-validation.md`.
